## Notes

- rsync 3.5.0 behaviour pinned with the binary for the plan's open question:
  - an identical file is removed (`--remove-source-files` removes what is in sync), also with `--size-only`;
  - `--existing` keeps a file that the destination does not have, but still removes an identical one;
  - `--ignore-existing` keeps every file the destination already has, identical or not;
  - `--update` keeps a file whose destination copy is newer;
  - `--dry-run`, a filtered file, `--max-size` and a failed transfer all keep the source.
  The engine models this with a `decision` enum (transfer / in sync / excluded from the list).
- Deviations from the plan:
  - the statistics counters are `sync/atomic` typed counters instead of fields behind a mutex;
  - the key set gains `files_removed` next to `files_deleted`, so that `--delete` and
    `--remove-source-files` are not mixed in one number (README documents the keys);
  - `--stats` is printed for every run that reaches the execute phase; a run that cannot
    list a source or the destination still aborts with code 23 before there are counters;
  - a dry run prints `would remove` lines for `--remove-source-files` (rsync is silent there);
  - the temp-file spill (`seekable`) of the S3 driver is gone: the multipart uploader buffers
    16 MiB parts in memory instead, which the limiter wrapper made necessary anyway. An object
    whose size is unknown up front is capped at 10,000 parts (160 GiB at 16 MiB); a seekable
    body, such as a local file, lets the SDK grow the part size instead;
  - `--parallel -3` is rejected by kong as an unknown flag (usage error, exit 1) before the
    engine check runs; `--parallel 0` hits the explicit usage error.
- Fixed a latent bug in `internal/storage/memory`: listing below a namespace reported a zero
  `Size` and `ModTime`, because the information was looked up by the relative key instead of the
  full key. It was invisible while every test compared a file against an empty destination.
- New dependency: `github.com/aws/aws-sdk-go-v2/feature/s3/manager v1.21.1` (same SDK family, no
  third-party code).
- Verified against LocalStack (`localstack/localstack:3.8.1`, port 4566): the S3 integration tests
  pass, including the new multipart test; a smoke run moved a 32-file tree (one 20 MiB object, two
  parts) up and back down, a dry run left the bucket untouched, `--remove-source-files` emptied it, and
  `--bwlimit 100` moved 200 KiB in ~2.0 s in both directions.

## Follow-up: S3 transfer dependency update

- `feature/s3/manager` v1.23.28 deprecates `NewUploader`/`Uploader` in favour of
  `feature/s3/transfermanager` (4 staticcheck SA1019 findings, deprecation warnings in the
  docs). The driver now uses `transfermanager` v0.5.11 (`New` + `UploadObject`), so `manager`
  is gone from `go.mod` again and `golangci-lint run` is back to 0 issues.
- Mapped options: `PartSizeBytes` (16 MiB default), `MultipartUploadThreshold` = part size so
  that an object smaller than a part stays a single `PutObject`, `Concurrency` from `--parallel`.
  Abort-on-error is built into the manager, so the old `LeavePartsOnError: false` is implicit.
  Metadata, `CreateMultipartUpload` metadata copy and checksum handling behave as before.
- Bonus: `UploadObjectInput.ContentLength` would let the driver declare the size of a
  non-seekable body, which lifts the 160 GiB/10,000-part cap. It is not wired yet, because the
  `storage.Endpoint.Create` seam does not carry the size.
- Re-verified against LocalStack: S3 integration tests (single + multipart, mtime round-trip)
  pass, `go test -race ./...` passes, and the CLI smoke run is unchanged: 32 files up (a 20 MiB
  object with ETag `...-2`, i.e. two 16 MiB parts; a 1 MiB object with a plain ETag), dry run
  touched nothing, `--remove-source-files` emptied the bucket after an identical tree came down,
  `--bwlimit 100` took ~2.0 s for 200 KiB in both directions.

## Follow-up: sized uploads

- The engine now hands the size of every file to a destination that can use it:
  `storage.SizedCreator` (optional capability, like `Copier`/`ModTimeAware`) with
  `CreateSized(ctx, key, modTime, size, r)`; `Endpoint.Create` is unchanged, so no driver was forced
  to grow a method. `syncengine.copyFile` passes `it.info.Size` from the listing.
- The S3 driver implements it and sets `UploadObjectInput.ContentLength`, which is what the transfer
  manager needs to plan the upload: it grows `PartSizeBytes` when an object would need more than the
  10,000 parts S3 allows, so the 160 GiB ceiling of an unknown-size body is gone and the full 5 TB an
  object may hold works. The declared size is only advisory for planning — `mapSingleUploadInput`
  does not turn it into an HTTP `Content-Length` — but S3 validates it as `MpuObjectSize` when a
  multipart upload completes, so a source file that shrinks mid-transfer is reported as an error
  instead of storing a truncated object.
- Tests: `TestRunTellsTheDestinationTheSize` (memory endpoint wrapped to record the size), the
  multipart integration test now uploads through `CreateSized`.
- Verified on LocalStack: local → S3 and S3 → S3 of a 20 MiB object both produce the same two-part
  ETag (`…-2`) and a 1 MiB object stays a single request; contents are byte-identical after coming
  back down; the preserved mtime survives both hops. `golangci-lint run` 0 issues, `go test -race
-count=1 ./...` green.
- Not covered by a tong test: the part-size growth itself, which needs an object of more than
  48 GiB (10,000 × 5 MiB) or a fake S3 API. The propagation is SDK-tested upstream.
